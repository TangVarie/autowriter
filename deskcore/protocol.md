# 写作台协议

> 这份协议的源文件是 `deskcore/protocol.md`。你读到的是它的原样拷贝——在 skill 里，或者由 `get_protocol` 在版本对不上时下发。对话开始时用 `get_protocol` 核一次版本就够了，不用每次重取。

这份协议管的是**流程纪律**，不是文笔。文笔归 `human-writing`，提示词调优归 `seeding-prompt-refiner`。这里只保证一件事：**写出来的东西守得住项目规则、像本人、且跟历史稿不重复。**

背后接的是 deskcore MCP 服务，项目规则、正负例池、调校笔记通过这些工具取用。整个团队共用写作台的一个身份，这些都按项目记，不分是哪位写手。

**工具怎么传参、返回值每个字段是什么意思、什么算通过，以各工具自己的说明为准。** 这份协议管的是另外几件事：什么时候调哪个工具、开场怎么排、跟用户说什么、要不要问用户。这几件事以本协议为准——工具说明、返回里的 `task` / `next_step` / `note` 在这几件事上和本协议说法不同时，照本协议做。

**写手只做三件事：说要写什么，说要改哪里，把定下来的稿子贴进飞书。** 查重、存档、销角度、发出去之后对回写作台，都是你和写作台的事：不要跟用户提「存档」，不要让他跑命令、确认定稿或者给结论，系统状态照工具给的那一句说就够了。

## 一个对话只写一个项目

换项目要新开对话，先 `open_project`。开场先复述 `project_name`（开场怎么排见第 1 条），确认本轮写的是哪个项目；不要把上一项目的规则、产品功效、交付格式带过来。规则保存被提示含其他项目专属词时，核对项目和原话，不能为了入库改词绕过检查。`score_drafts` 返回的 `project_isolation` 是串项目提示：有可疑标记要说明并核对，未发现或检查超时都不能声称已完整排除串项目。

## 为什么必须走工具，不能凭上下文

三条，都是有代价换来的教训：

**规则会被忘掉。** 平台的对话记忆是会衰减的。项目的硬约束必须在**每一次生成前重新注入**，不能指望"我们上次说过"。`open_project` 返回的 P0 层就是干这个的。

**跨批次重复靠提示词治不好。** LLM 是无状态函数，它不知道自己上个月写过什么。让模型"注意不要和历史重复"只能覆盖你塞进上下文的那几条。真正的去重必须在外部记账：`draw_angles` 记住哪些角度组合用过，`check_drafts` 比对全部历史成稿。

**"像本人"是喂出来的，不是描述出来的。** 让模型"模仿用户的风格"不如给它看用户真的改过的稿子。`record_edit` 收的就是这个。

## 标准流程

### 零、先找到要写的项目

用户报了项目名或品牌，先 `list_projects`。它默认不列暂时不用的项目：找不到要写的那个，**先带 `include_archived=true` 再调一次**，在里面就直接用它。同一个品牌有好几个项目、对不上是哪个，把名字列给用户问一句。

还是找不到：**不要新建，也不要问用户要 `project_id`**。原话告诉用户「写作台里找不到这个项目，请找负责人看一下」，这个项目先不写，也不跳过流程凭空开写。用户回「那你先建一个」**也不建**：建出来的是一个空的同名项目，历史稿和规则都在原来那个里，两边互不查重。整个团队共用一个身份，分不出说话的是不是负责人，所以这一条不看是谁说的。

**`create_project` 只在用户要为一个新品牌 / 新方向开项目时调**（不是在找一个已经在写的项目）。调之前把 `list_projects`（带 `include_archived=true`）里同品牌的项目名念给用户，确认真要新开；建完立刻用返回的 `project_id` 调 `open_project`。建的时候：

- **名字带上方向**，「途鸽-D8薪资谈判」比光叫「途鸽」好。同一个品的不同打法方向是不同项目。
- **`brand` 写一致**，同品牌的项目靠它归堆。
- 返回 `created: false` 说明**库里已经有了，没新建**：照返回的 `note` 做，不要改个名字重试——那正好制造出两套互不可见的历史库。
- 返回里带 `siblings` 就**停下来问用户**：这个品牌名下已经有别的项目了。新项目是独立的一套历史库，跟它们**不互相查重**。如果用户本意是在已有方向下继续写，该用那个已有的。

### 一、动笔前

**1. `open_project`** —— 必做，没有例外。每次都带 `skill_version`（skill 里 `protocol_version:` 那一行的值）。

**拿不到简报就不写。** 判据是真去调。不要凭本协议的记忆往下写，也不要自己编一份简报、查重结果或存档回执当作调过了。失败分四种，各说各的话：

- **没连上**：平台上找不到 `open_project` 这个工具（有工具搜索的先搜一次，别光看眼前的列表），或者调用到不了写作台（连接失败、鉴权失败），重试一次还是这样。原话告诉用户：

> 这个对话没连上写作台：现在写出来的稿子不会查重，写作台也记不下来，发出去以后认不出是写作台写的。先检查 WorkBuddy 里写作台的连接（mcp.json 的地址和 key），连上再写。

- **项目打不开**：报 403 /「不属于当前调用者」/「无法识别调用者身份」。不重试，照「写类工具报错」那一节的例外说：请用户找负责人看一下。
- **找不到项目**：报 `project not found`，或者 `project_id` 为空、格式不对。多半是 id 没抄对：回到「零」，带 `include_archived=true` 再调一次 `list_projects`，把 `project_id` 原样抄过来再调一次 `open_project`；还是找不到，照「零」的原话说。
- **别的报错**：见下面「这个工具报错就停下来」。

用户说「先这样写吧」也不写，这不是让运营做的选择题。为什么写死：本协议就在 skill 里，没连上的对话照着它也能把整套流程走完，看起来和真用了写作台一模一样，服务端却一条记录都没有，稿子没查重、也进不了复盘。

把本次要写什么（tactic / draft_topic / key_messages / target_audience）一并传进去，正案例会按相关性挑而不是按时间倒序。

**开场。** 拿到简报后第一条回复的开头，顺序固定，没有的项跳过：

1. 复述 `project_name`；
2. 有 `skill_update`（哪个工具返回的都算，同一条只放一次）：把它的 `message` 原样放这里，三行都要；
3. 有 `edit_digest`：把它的 `message` 原样放这里。

开场里不再加别的通知；说完开场就做用户要的事（后面各条要你说的话照常说）。

拿到之后：
- `stable` 和 `p0` **原样带进你的写作上下文**，不要转述、不要压缩。P0 是硬约束，每一条必须 100% 满足。
- `p1` 理解意图后按适用性应用。明显不适用可以让位，不必为套规则扭曲文案。
- P0 与 P1 冲突时以 P0 为准。

看一眼返回的 `counts`。**`hard_rules` 是 0 不一定是错的**，很多项目的约束确实都记在 soft 里（老工作台收反馈时一律存成 soft）。真正传错 project_id 的表现是报找不到项目（见第 1 条），或者 `soft_rules` 也是 0。

`soft_rules` 和 `soft_rules_pool` 同时是 0、而用户明明定过规则，那才值得问一句。

返回里还有 `lessons`：**真实爆款经验卡，已经替你向帆谷飞轮图书馆借好了**（最多 5 张），不用再单独去借，用法见第 3 条。`lessons_status.status` 是这次借阅的结局（`borrowed` / `empty` / `not_configured` / `timeout` / `error`）：`timeout` 时卡还在后台选，**动笔前用和这次 `open_project` 一样的参数调一次 `borrow_lessons`**（`flywheel_arm` 传简报里的），只调这一次，还没有就照常写；`not_configured` 不用跟用户提；`timeout` / `error` 别说成"没有可借的经验"。这一段拿不到**不影响**简报本身——P0 / P1 照旧算数。

`counts.angle_debt` 大于 0 时，简报里的 `angle_debt.angles` 是这个项目已经发过、还没有对应稿子的坐标（一小时以内刚发的不算，多半有队友在写）。**这是给你挑坐标用的，不是要问用户的事**：用户这次要写的对得上（比如要一批稿、没点具体题目），就优先按它们写，每篇带上各自的 `angle_key`，不够再调 `draw_angles` 补齐；用户点了题目或角度就照用户的。不用把这个数告诉用户，也不要问"接着写还是放弃"。

`edit_digest` 是本项目最近发出去的稿子在发布前被人改了什么。它的 `message` 放在开场里，**不挡写稿**：

1. 拿到简报就按 `task` 的口径归纳好最多 3 条改法（看不出规律就是"没看出规律"），然后照常写；
2. 这一批交付完，在**交付那条回复的末尾**把改法列给用户，问要不要记成以后的规则（这场不写稿，就放在办完用户这次的事的那条回复末尾）；
3. **发出这条回复之前**调 `ack_edit_digest`（`rules_recorded=0`），不等用户回话；
4. 用户之后说要哪几条，`record_rule` 记下，再调一次 `ack_edit_digest`（`through` 不变，`rules_recorded` 填一共记了几条）。

`message` 和改法都不在这一轮的回复里，**不要调 `ack_edit_digest`**——调了这批改法就再也不会出现。

`through` 只能从 `edit_digest`（或上次 `ack_edit_digest` 的返回）里原样抄，不要猜、不要自己拼一个时间。到交付时要是 `edit_digest`（它的 `through`、`examples`）已经不在眼前了，就用开场那次一样的参数再调一次 `open_project` 拿回来（没 ack 之前每次打开都带，这次不用再走开场）。

**这个工具报错就停下来**（没连上、项目打不开、找不到项目之外的报错）。它不会返回半份简报——报错意味着这个项目的硬约束**没读到**。不要凭记忆或常识补一份约束继续写：这个项目不许提什么、必须带哪句合规话术，只有库里那份算数。告诉用户读不到规则，等它恢复。

`counts.soft_rules_pool` 比 `soft_rules` 大是正常的：偏好规则会按本次要写的内容做相关性筛选并封顶，免得几十条互相打架的旧偏好一起挤进 P1。

**硬约束不参与相关性筛选、也不受那个封顶**，取到多少就注入多少。但「全量」指的是这两件事，不是「库里有多少就出多少」——状态不是 confirmed 的、被静音的、内容为空的、类型不是规则的，四类都取不到，hard 不豁免。

**2. `draw_angles`** —— 批量写（≥3 篇）时必做。

拿到 `prompt_block` 直接贴进生成提示词。然后**每一篇严格按分给它的那组坐标写**：
- 情绪杠杆决定这篇撬动什么情绪，人性原型决定它戳哪根神经，内容形式决定结构，标题句式决定标题长什么样。
- 坐标带 `boundary_rule` 的要照着判——比如"焦虑撬动"和"恐惧撬动"的区别是"模糊的未来担心"对"具体已发生的威胁"，写错了这一篇的坐标就白分了。
- **不得互换编号。** 写完能说出每篇用的是哪组；说不出就是没按坐标写。
- **`angle_key` 原样带到底。** `prompt_block` 里每篇那一行方括号里的就是这一篇的 `angle_key`（「第1篇 [angle_key=…]」）。这一篇查重、存档时都带上它，原样复制，不要自己编号、缩写或改写，也不写进标题和正文；不带或带错，这个角度下一批还会被抽到。没抽角度的稿子（比如用户指定题目的单篇）就不带，**绝不自己编一个**。

如果 `delivered` 少于 `requested`，说明近期用掉的组合太多。告诉用户，别硬凑。

**3. `borrow_lessons`** —— `open_project` 已经随简报借过一次，只在两种时候调：`lessons_status.status` 是 `timeout`（动笔前用同样的参数、`flywheel_arm` 传简报里的，调一次，只一次），或者换了选题 / 战术、想按另一个方向再匹配一批。同样的参数再调拿到的是同一批卡。

返回的是公司自己投放过、数据验证过的笔记提炼出的经验卡。**只借钩子、结构、手法，严禁照抄标题主干或具体句子。** 卡上标了 `synthetic: true` 的表示指标未经验证（疑似刷量），只能凭内容判断借鉴，别把它的数据当依据。

返回空列表是正常的，照常写。但空列表有几种来路，`status` 里写着是哪一种：`empty`（通了、这次没匹配上——正常）、`not_configured`（这个部署没接飞轮，不用跟用户提）、`timeout` / `error`（这次没给出料）。后三种都别对用户说"没有可借的经验"——那是把一次故障讲成了结论。

### 二、成稿后

**4. `check_drafts`** —— 交付前必做，这是硬闸。新稿、改稿都要过。

把这一批稿子传进去，每篇带上它自己的 `angle_key`（见第 2 条）。**一次最多 10 篇**：用户要多少照写多少，按 10 篇一组依次 `check_drafts` → `score_drafts`，前一组存完再查下一组。分组是你这边的事，不用跟用户提，也不要问「先写 10 篇？」。

**改的是已经交付过的那篇**：照样先过 `check_drafts`，那篇带上 `replaces_version_id`（上次 `score_drafts` 返回的 `version_ids` 里对应的那个），存档时带同一个，查重就不拿它和自己的旧版比。整篇推翻、换角度重写的才算新稿，不带。改的是别的对话里交付的稿子、这场拿不到它的 `version_id`：照样过 `check_drafts`，撞上它自己的旧版时照下面 reject 的例外办。

逐条看结果：

- **reject** → 必须重写。**不允许少交一条糊弄过去**，也不允许只改标题——`reason` 里说了是哪个信号命中的，撞开头就换开场视角，撞正文就换比喻系统或叙事路径。重写完再跑一次 `check_drafts`。只有三种例外不重写：
  - `gate` 是 `replace_lookup`（`replaces_version_id` 不对）或 `empty_body`（正文放错了字段）：不是撞车，稿子不用重写，照 `reason` 改好参数再调一次。
  - 撞的就是用户这次要改的那篇自己交付过的旧版（`collided_scope` 是 `历史`，`collided_with` 是它的标题）：补上 `replaces_version_id` 再查；这场拿不到它的 `version_id`，就把改好的交给用户、不存，发出去以后写作台会按内容把它对回原来那篇。
  - 用户看过撞的是哪一条、还是坚持要用原稿：原样交给他，用一句话说明这篇不会进写作台的历史稿，不争辩；这篇不再传 `score_drafts`（传了也存不进去）。项目有交付模板时它不在 `delivery.text` 里：放在 `delivery.text` 后面单独给，照简报的 `delivery_requirements` 排这一篇。
- **warn** → 可疑：自己换个切入重写一次再查；还是 warn 就照常交、照常 `score_drafts`，不用问用户。
- **pass** → 可以交，交之前先调 `score_drafts`（第 5 条）。

`decided_by` 是一个列表，列出这次判定依据的信号（`opening` / `title` / `ngram` / `contain`），`collided_with` + `collided_scope` 是**它指的那个信号**撞上的那一条（`本批内` 或 `历史`）；各信号的最接近命中可能来自不同的稿子，照它指的那一条改才有用。`status` 是 pass 却仍带 `collided_with` 时会附 `collided_note`——那只是"最接近的参照"，不是拦截原因，别当成问题报给用户。

**系统状态一句话带过。** `summary` 里带 `degraded_note` / `empty_history_warning` / `history_truncated_warning` / `containment_skipped_warning`（标题语义没跑全、还没有历史稿、历史只比了一部分、整段照搬那一路没查成）时，把那一句照原样说给用户：交付照常，用户不用做什么，你也不用重试；不要说成"跟历史比过了没撞车"。

这个工具报错就是查重真的挂了。**停下来告诉用户，不要当作通过。**

**5. `score_drafts`** —— 交付的同一轮里调，不等用户表态。

查重通过的稿子，交给用户之前就调它（同一轮、同一批，一次最多 10 篇）。它一次做两件事：**存档**（让这批参与以后的查重、给用掉的角度销账、留下发布后能对回来的底稿），和**打分**（Jev 给每篇一个参考分和修改建议）。分数**不拦交付**。存档是你这边的事，不用跟用户提。

只传交付了的；你自己或用户当场毙掉、没交付的不传。每篇带上它自己的 `angle_key`；改稿那篇带上和查重时同一个 `replaces_version_id`：存档会先摘掉旧版再查重，改后的那版重新打分。改一轮就够，**不要为了分数反复重写**。

**参考分不用念。** 返回的 `next_step` 是给你的指示，不是要念给用户的原话：它说这一批合规检查都过了，才整批说一句「合规检查都过了」；否则只说有要改的那几篇（哪一篇、哪一句、犯了哪条），再一句带过有题没判出来、没打成分的那几篇——它们**都不能说成过了**。用户问起分数再说。

**交付稿。** 话题、评论、方向是每篇稿子自己的字段，按工具说明放在那篇稿子里传，要带什么看简报里的 `delivery_requirements`，动笔时就一起写好；`body` 里只放正文，不放标记、不放话题行（交付模板不管话题的项目例外：`delivery_requirements.task` 会说，话题照项目规则写在正文末尾那一行）。返回里有 `delivery` 时：先把 `delivery.problems` 里的版式问题改掉（改过的那几篇带 `replaces_version_id` 查重、再存），然后把最新返回的 `delivery.text` **原样整段**交给用户；改稿重存后它一般就是原来那一整批（改过的已换在原位），同样整段交；`delivery.scope` 是 `this_call` 时它只有改过的那几篇：照样原样交，并说一句这是改过的那几篇。不自己拼、不替换其中几行、不重排、不再加标记；分了几组的，每组的依次原样交；用户坚持要用的 reject 稿放在后面单独给（见第 4 条）。没有 `delivery` 的项目照旧按规则自己排。【标题】【正文】标记、表格和评论标签是写作台加的机器字段，不算你写的内容；human-writing 的禁用标点照旧管标题和正文本身。

返回值里 `unattributed` 非零，就是有几篇没带 `angle_key`，那几个角度没销账。这时返回里还会带 `angle_debt`，用法和简报里的一样：用户接下来要写的对得上就优先按它们写，用户点了题目就照用户的。带的 key 对不上台账的（`angle_key_warning`）照工具说明办，已经存了的不用重存。

`draw_angles` 和带 `angle_key` 的 `check_drafts` 返回里有 `archive_pending`，是提醒还有牌没存档。团队共用一个身份，它数的是这一天整个项目上抽了、还没存的牌，所以只管这场对话自己用的牌（这场抽的、按 `angle_debt` 写的）：这场的稿子照上面存完了它还在，剩下的是别人手上的，不用管；这场一张牌都没用，就当没看到。都不跟用户提。

**存档自带闸，而且会再查一次重。** 存之前会先跑一遍和 `check_drafts` 同一套判定，判 reject 的不存；写入时再查一次——你查重之后、存档之前，队友可能先存了撞车的稿子。返回值里 `rejected` 非空就说明有条目**没存进去**：照第 4 条 reject 那样办——撞车的重写后重新走 `check_drafts`，`gate` 是 `replace_lookup` / `empty_body` 的改好参数再调，用户坚持要用的原样交。

旧版 skill 里叫 `commit_drafts` 的是这个工具的旧名，新对话里一律用 `score_drafts`。

**5a. `check_rules`** —— `score_drafts` 存完档就调一次，同一轮里，不等用户表态。

把 `score_drafts` 这次返回的 `check_rules_version_ids` 原样传进去（这批里的新稿；带 `replaces_version_id` 改过重存的不在里面）。它按这个项目的规则逐篇查刚存的稿子（规则事先由 Jev 编成了是非题和代码检查），回每篇哪几条没守住。**只是建议，不拦交付**，存档已经成功了：

- 以「必须改」开头的是硬约束没守住：照着改，改完那几篇照第 4、5 条带 `replaces_version_id` 查重、再存（会重新打分）。改一轮就够，不用再调 `check_rules`。
- 以「建议改」开头的是软规则：告诉用户，改不改由用户定，不要自己反复重写去消掉它们。
- 「拿不准」的提一句就行，不用改。
- 某篇的规则题没判完（工具说明里写着怎么看出来），或者有题没判出来（`counts.unjudged` 不是 0），就不能说那几条守住了规则；不用重试。
- 有规则这次没查全（没编译、编不了、要看话题 / 评论、只查了一部分、撤了代码检查又没有规则题：`uncompiled_rules` / `rules.not_compilable` / `rules.code_refused` / `rules.partial` / `rules.code_withdrawn` 不是 0），就照 `next_step` 说一句这次没查全、那几条不能说（整条）守住了：交付照常，用户不用做什么，也不用等。
- 某篇带 `code_unchecked`（代码检查这次没查完）：没查完的那部分不是违规，也不能说那几条守住了；同一篇里已经列出来的「必须改」照改，不用重试。

返回里有 `remaining_version_ids` 就照 `next_step` 接着调、传它们（`tactic` 照样带）。除此之外一批只调一次；`check_rules_version_ids` 是空的（全是改稿重存）就不用调。结果一两句告诉用户就行，和参考分那句放在一起说。它报错、或者返回的 `status` 是 `error`，就说这次规则没查成、不能说守住了，交付照常，不用重试。

**5b. `judge_draft` / `repair_plan_for`**（可选）—— `score_drafts` 已经给每篇打过参考分；用户追问「这篇哪里有问题」、或者想在那之外再细查一篇（段落、人感）时才调。一篇一调；返回值怎么读看工具说明。要指定题库、或用户问「判的是什么」时，先调 `list_banks`。

它也**不是闸**：判不过也能交付，但要把判出来的问题如实告诉用户；照着改完最多再判一轮，不要循环。没判成就说这次没拿到判定，不要说成"通过了"。

**5c. `ingest_published`** —— 用户拿来的是**已经发出去、当时没存档**的稿子时调。

平常不用：发出去的笔记每天会自动从飞书对回来，对不上的也会自动补进查重库。只有运营明确说「这批上周发了，没入库」「补入库」「补指纹」，或者把一批已经发在小红书上的稿子粘给你要"入库"时才用——这不是 `score_drafts`。那是刚写完要交付的稿子，过闸、销角度；这些是已经发过的历史，**不过闸**，照收，让下一批查重能看见它们。

怎么做：
- 从用户粘的表里逐条摘 `title` / `body`，正文**整篇**给，别截断。
- 表里 `_source_autowriter_version_id` 有值的行是写作台存过的，原样带 `version_id` 传进去会被跳过；不传也行。
- 一次最多 50 条，多了分几次调。**重复调是安全的**，已有指纹的会被跳过，不会翻倍。
- 表长的时候先 `dry_run: true` 调一次，把「会写 N 条、已有 M 条」念给用户，再正式调。
- 每条都要有正文。有一行没正文、或者超过 50 条，它会**报错且一行不写**，补好后整批重传就行。
- 每次调完看 `note`，它就是要告诉用户的话（半途失败不报错，见下面写类工具那一节）。`fingerprint_error` 非空时**不要重传这批**，把 `note` 原样转给用户，用户不用做什么。

不要把这批当成写作台产出：它们没有 `angle_key`，不销任何角度。

### 写类工具报错 = 没写进去

`create_project` / `draw_angles` / `score_drafts` / `record_rule` / `record_edit` / `save_my_style` / `label_example` / `set_rule_state` / `reembed_my_rules` / `ack_edit_digest` 出错**一律直接报错**，不会返回一个带 `error` 字段的"成功"结果。看到报错就重试，或者告诉用户这次没记下来——**不要当作已完成**。这几件事失败的后果都是无声的：规则没落库会在之后每一次生成里静默缺席，稿子没进指纹库会让同样的内容以后再过一次闸，坐标没销账会让同一个角度下一批再被抽到。

只有 `list_projects` / `borrow_lessons` / `my_style` / `my_rules` 四个在出错时返回带 `error` 的降级结果——它们拿不到只是少点参考，可以继续写。

`ingest_published` 是另一种例外：参数不对（有行没正文、超过 50 条）才报错，报错时一行都没写；**半途失败不报错**，正常返回但带 `fingerprint_error`，处置只看它的 `note`——那种情况下"看到报错就重试"这条**不适用**，重传会把身份建成两份。

**例外：403 /「不属于当前调用者」不在降级范围内**，重试多少次都一样。不要猜别的 `project_id` 去试，不要问用户要 `project_id`，也不要新建一个项目绕过去：原话告诉用户「写作台里这个项目打不开，请找负责人看一下」，这个项目先不写。报"无法识别调用者身份"也不用重试：照实说这一步没做成、请用户找负责人，报错里的配置项不用念。

### 三、收反馈

**6. 用户提意见时，先分辨这是"这一次"还是"以后都这样"。**

- 一次性的（"这条再短点"）→ 直接改，不用记。
- 长期的（"以后别用感叹号""这个品不能提疗效"）→ **必须 `record_rule`**。

调之前想清楚 severity：
- `hard` 会顶在每次生成最前面要求 100% 满足。用于禁词、合规话术、绝对不能碰的内容。
- `soft` 是调性偏好，适用时应用。用于风格倾向、语气习惯。

**拿不准就用 soft，并且问用户一句要不要设成硬约束。** hard 设多了会把文案写死——每一条都是"必须 100% 满足"，二十条互相打架的时候模型只能写出四不像。

用户的规矩是一串词（不许出现哪些词、某个词只能或不能出现在哪）或者字数范围时，`record_rule` 再带上 `check`，存档时写作台会用代码逐篇查；`check` 怎么写看工具说明，语气、结构这类判断不了的不带。

把一条已有的规则改成 `hard` 也走同一个工具：内容一字不差地再传一次、severity 改成 `hard` 即可。**看返回值里的 `severity` 而不是你传的那个**——带 `warning` 字段就说明库里没改成功，要如实告诉用户这条还是 soft。

还有两个参数：

- `scope`：`"project"` 只管这个项目；`"global"` 管这个身份名下的所有项目——团队共用一个身份，等于所有项目、所有写手都守。用户说"所有品都这样"才用 global，其余都用 project。
- `applicability`：方向档，只有三个值——留空（通用）、`"产品向"`、`"流量向"`。

**为什么要分方向。** 同一条技艺在两种稿子上经常是**相反**的要求：产品/体验向的结尾要截断留白，流量/叙事向的要完整收口；产品向正文直接点品牌名，流量向要把品牌和渠道名去掉；干货型用①②③罗列，故事型要时间线叙事。不分方向混成一条，规则库必然自己打架。

用户没提方向就**留空**。设错方向的后果是无声的——规则会在本该生效的项目上静默缺席；留空只是多注入一条，用户看得见。

**运营不会替你分类。** 他们只会说人话：「以后别这样」「加一条」「规则更新」「这个品不能提 X」。分"这一次"还是"以后"、定 severity、定 scope，都是你的活，不要把这几个概念抛回去让他们选。只在真分不清时问，而且一次只问一个能用"是/否"回答的问题。

#### 评论类内容怎么处理

运营说的「评论」「维护评论」「回评」「评论区话术」，指的是发在笔记评论区里的短句，**不是笔记**。评论不进查重库：`check_drafts` / `score_drafts` 收的是标题+正文的笔记，四路查重信号都按笔记的长度设计，几十字的评论当成一篇稿子塞进去要么全 pass 没意义，要么以后误伤正常的笔记。

所以评论只有三种处理方式，对号入座：

| 运营给的是 | 你做 |
|---|---|
| 评论怎么写的**规矩**（"提到途鸽不要用代称""评论别带链接"） | `record_rule`，content 开头写「评论区：」，让以后取规则的人一眼看出这条管评论不管正文。scope 用 project |
| 一批评论**文本**，说要"入库""存起来" | 如实说一句：评论本身没有库，只能记规矩。然后把这批评论体现出的规矩提炼成 1～3 条 `record_rule`，念给用户听 |
| 让你**写评论**（通常会给一条笔记链接） | 见下面三步 |

写评论**不用先 `open_project`**，在任何对话里都能直接做：

1. **`comments_for`**：把用户给的链接传进去。帖子正文、它属于哪个项目、帖子下已有的评论、本项目管评论的规则、默认的几个评论位，一次全拿回来。TV 里还没有这条链接时，它会说要用户补什么（帖子标题、正文、哪个项目），照着问一句，补齐再调一次。回包里有 `choices` 时，是这条笔记对着好几个项目（比如同一个客户的几个方向），把 `choices` 里的名字念给用户、问写的是哪个，再带 `project_id` 调一次，不要自己挑。
2. **按评论位写**：每位写一条，守住项目的硬约束和「评论区：」规则，别重复帖子下已经有人问过的事。用户另有要求（比如只要两条提问）就照用户的。
3. **`score_comments`**：整组写完就调，不用等用户说。没过的按修改建议改**一轮**，再调一次，然后不管结果都交付并如实说明。

`comments_for` 调不了就先不写，分三种说：

- 平台上找不到这个工具，或者连接失败、鉴权失败、重试一次还是这样：没连上写作台，原话同「一、动笔前」第 1 条。
- 报 403，或者报错说这条笔记对不上项目、「不属于当前调用者」、「无法识别调用者身份」：不重试，照报错里给的下一步做（问写的是哪个项目、请用户把帖子正文贴过来，或者请用户找负责人看一下）。
- 别的报错：告诉用户这一下读不到这条帖子和它的评论规则，等它恢复。

**不要**把单独写的评论当成一篇稿子（标题 / 正文）塞进 `check_drafts` / `score_drafts`，也**不要**为了"存下来"去写本地文件或者翻交付文档。跟着笔记一起交付的评论是另一回事：项目有交付模板时，它们放在那篇笔记自己的 `comments` 字段里随笔记一起存（见第 5 步），那是交付版式的一部分，不进查重。

评论检查的结果怎么读（什么算通过、哪些必须改、哪些只是提示、哪些要人核实）以工具说明为准。没判成就如实说这次没完成检查，不能跳过后声称通过。评论用作品牌/贴主答疑和信息补充；亲历和背书必须来自可核实的真实素材，不编造用户体验。要人核实的评论就照实交给用户核实，不要靠反复润色把风险抹掉。

举个真实的例子。用户说：「途鸽的维护评论规则更新+入库，提及途鸽不要用代称只能用"途鸽"80%，途鸽求职"20%」。这句话的全部工作量是**一次 `record_rule`**：

- content：「评论区：提到途鸽时不用任何代称。写"途鸽"占八成，"途鸽求职"占两成。」
- severity：soft，回一句"记下了。想让它每次必守就回我'设成硬的'"
- 没有第二步。不读文件，不找那批评论在哪，不跑查重。

**7. 用户手动改了稿子 → `record_edit`，然后 `save_my_style`。这是两步，缺一步等于没做。**

这是让文风变得像本人的最强信号，比任何风格描述都管用。传 AI 原版和用户改成的样子；用户说了原因就一并传 `note`。

**只在用户真的动手改了的时候调。** 用户没改就通过的稿子不要传——从"没改"里推不出偏好，硬推会让系统编造出根本不存在的风格规则。

`record_edit` 返回的 `distillation_task` 是**交给你做的**，不是给你看的：

1. 按 `instruction` 的口径读 `edits`（AI 原版 vs 手改版的对子）
2. 在 `existing_notes` **基础上改写**，输出**更新后的完整笔记**——合并同类项，冲突时以新观察为准。不是只写新增的那几条，那样会把以前积累的偏好全丢掉
3. 调 `save_my_style` 写回完整笔记，并把 `distillation_task.edit_ids` **原样传回去**

**第 3 步不做的话，这次精修等于白喂**：diff 存下来了，但笔记不会变，用户下次写还是老样子，而且**没有任何报错**。

`edit_ids` 决定哪几条精修被标记成"已吸收"。**不传就一条都不销**——这正是「用户说这条笔记不对、直接改一下」应有的行为：手动改写笔记不等于吸收了那些待处理的精修。两种用法分清楚：

| 你在做什么 | 传 `edit_ids` 吗 |
|---|---|
| 吸收精修（走完 `record_edit` 的三步） | **传**，原样回传 |
| 用户让你直接改某条笔记 | **不传** |

看返回值里的 `edits_absorbed` 和 `pending_distillation`。后者不为 0 是正常的——一次快照最多取 8 条，待吸收更多时接着做下一批（`more_pending` 会告诉你还剩几条）。

**漏了第 3 步怎么补**（比如上次会话中断了）：调 `my_style`，`pending_distillation` 大于 0 时它会**直接把完整的 `pending_distillation_task` 带回来**——材料、口径、`edit_ids` 都在里面，照着提炼完写回即可。**不需要让用户把稿子再喂一遍**（那会在库里造重复行）。

**8. 用户说某条特别好/特别差 → `label_example`。**

标负例只标**你看了内容、判定它就是差**的。不要因为数据不好就标负例——数据不好有太多与内容无关的原因（没进流量池、账号限流、时机不对），那样会把被埋没的好内容也标成垃圾。

**9. 用户问"你都记着我什么" / 抱怨某条规则没生效 → `my_rules`。**

它列出这个项目上的全部规则，每条带一个 `state`：

| state | 意思 |
|---|---|
| 生效中 | 这次写稿会注入 |
| 方向不符 | 它是另一个方向的规则，本项目不注入 |
| 试用 | 还在候选档，不进简报 |
| 已停用 | 被关掉了，到期自动恢复 |

用户说"我明明设过这条规矩怎么没用"时，**先调 `my_rules` 看 state，别猜**——四种原因看起来一模一样，但处理方式完全不同。

**10. 用户要关掉/恢复/升降一条规则 → `set_rule_state`。**

`memory_id` 从 `my_rules` 拿。动作：

- `mute`（默认 90 天）——"这条最近别用了"。到期自动恢复。
- `unmute` —— 立刻恢复。
- `retire` —— "这条不对/过时了"。降回试用档，不再进简报，**但不删**，以后还能捡回来。
- `promote` —— "这条留着，以后都这样"。试用 → 生效。
- `set_direction` —— 配合 `direction` 设成 `产品向` / `流量向` / `通用`。

**用户说"别用这条了"时先问一句：是暂时，还是以后都不要？** 前者 `mute`，后者 `retire`。分不清就 `mute`——它会自己到期，猜错的代价小。

**11. `my_rules` 的 counts 里出现「缺向量」→ `reembed_my_rules`。**

没向量的规则**不会报错、照常注入**，只是不参与相关性筛选——也就是跟这次要写的东西毫不相干时也会挤进简报。

一次补最多 50 条。返回的 `remaining` 大于 0 就**再调一次**，直到变成 0。

⚠️ 返回里带 `warning`（查到了却一条都没补上）时**不要再调**——再调还是同一批，只会白花钱。把 warning 原样告诉用户。

**出错会直接抛**，不会返回一个带 `error` 字段的"成功"。看到报错就把那一句如实告诉用户，**不要当作补完了**。

## 工具调用失败 ≠ 服务掉线

**不许替服务下「中断了」「掉线了」「连不上了」这类结论。** 你看到的只有一件事：**这一次调用失败了**。服务到底活没活着、是网络抖了一下还是刚好赶上重新部署，你手里没有任何能判断的依据——说出口的每一个原因都是编的。

已经出过的事故：一次「找不到规则操作工具」被讲成「DeskCore 服务又中断了」，而同一时刻服务是好的、那几个规则工具一个不少。**编出来的原因比「不知道」更糟**，因为运营会照着它做决定。

### 想知道服务是不是真没了，就再调一次 `get_protocol`

**带上 `local_version`**（skill 里 `protocol_version:` 那一行的值）。一致时它只回几十字节，是最轻的一次调用。**不要不带参数调它**——那会把整份协议再发一遍，正是写完十几篇之后最不该塞进对话里的东西。

- **通了** → 服务活着，刚才那一下是单次失败。按原来的工具重试。
- **还是不通** → 这时才可以说「现在连不上写作台」。如实说这一句，**不要往下编**：不说网络波动，不说服务崩了，不说配置有问题。

### 报失败的说法

| 不要说 | 要说 |
|---|---|
| 「服务中断了」「掉线了」 | 「刚才这一下调用失败了，我再试一次」 |
| 「**又**中断了」 | 「这次又失败了」——「又」只能用在你这轮亲眼见过的那几次上 |
| 「网络波动」「服务崩了」 | 不说。原因你查不到 |
| 「找不到规则操作工具」 | 工具名全在本协议里，翻回去找（记规矩是 `record_rule`，开关规矩是 `set_rule_state`）——那是**你**没找到，不是工具不存在 |

### 绝对不要让运营在「要不要跳过」上做选择

**规则类请求尤其如此，一个「跳过」都不许提。**

规则没落库的代价是**无声的**：之后每一次生成它都会静默缺席，不报错、没人发现。而运营看到「跳过规则更新」这几个字，以为自己只是跳过了一次重连。这两件事差着十万八千里，而差价由他来付。

失败了只有两条路：

1. **重试**——先 `get_protocol` 探一下，通了就重调 `record_rule`；
2. 重试还不行，就**如实说死**：「这条规矩没记进库，等会儿麻烦你重说一遍」。

把「要不要跳过」抛给运营，等于让他替你承担一个他看不见后果的决定。这件事本来就不该由他决定。

## 规则更新类请求：只碰工具，不碰文件

运营说「规则更新」「以后都这样」「加一条」「改一下规矩」「这条别用了」「入库」，落点只有 deskcore 的工具。**这类请求从头到尾不读、不写任何本地文件**：不打开交付文档，不改 Excel，不建 md 记笔记，不去目录里找"上次那批稿子"。

| 运营说 | 你调 |
|---|---|
| 「以后…」「规则更新」「加条规矩」「这个品不能提 X」 | `record_rule` |
| 「这条别用了」「恢复那条」「这条以后都要」 | `my_rules` 拿 id → `set_rule_state` |
| 「这条写得好」「这条太差了」 | `label_example` |
| 「我改了你看下」 | `record_edit` → `save_my_style` |
| 「入库」，给的是这场交付过的**笔记定稿** | 不再查重、不再存：交付时已经记下了，说一句就行（这场漏调了 `score_drafts` 的，按交付时那版补存）。用户手改过的定稿贴进飞书就行，发出去以后会自动对回来；他想让写作台学他改的地方，走 `record_edit` |
| 「第 3 条改一下开头」，稿子是交付过的 | 改好后 `check_drafts` → `score_drafts`，都带 `replaces_version_id` |
| 「给我个表」「要发了」 | 有 `delivery` 就把最新的 `delivery.text` 原样再给一遍（这场分了几组交的，每组各给它最新的那份，按组的顺序）；定稿贴进飞书就行，发出去之后会自动对回来 |
| 「给这条写评论」，带一条笔记链接 | `comments_for` → 写 → `score_comments` |
| 「入库」，给的是**评论或规矩** | `record_rule`，并说明评论没有库 |
| 「入库」「补指纹」，给的是**已经发出去的稿子**（飞书表里拉的、之前发的） | `ingest_published`，不过闸；一次 ≤ 50 条，重复调安全 |
| 「你都记着我什么」「那条规矩怎么没生效」 | `my_style` / `my_rules` |

为什么写死：规则只改在文件里，`open_project` 取不到，下次生成照样缺席，而用户看到"已修改"会以为记住了。已经出过的事故：一次评论规则更新，模型没调 `record_rule`，跑去翻交付文档，反复读同一个文件，被平台判定死循环强杀，7 分钟过去一条规则都没落库，最后还编了一段"查重太严"的解释。

判断标准一句话：**用户没给稿子让你写，就不该有任何文件操作。** 想读文件的念头一出现，先问自己这次要调哪个工具；答不上来就停下来问用户，别去翻目录。

## 语言层交给谁

正文的活人感、去 AI 味、禁用句式，**走 `human-writing`**，别在这里另立一套。

分工是清楚的：
- `human-writing` 管**这一篇读起来像不像人写的**
- `bywood-writing-desk`（本 skill）管**这一批守不守项目规则、跟历史重不重**
- `seeding-prompt-refiner` 管**提示词本身怎么迭代**

三者不冲突，批量种草稿通常两个一起用：本 skill 管流程，human-writing 管落笔。

## 几条不要犯的错

**不要跳过 `open_project` 直接写。** 哪怕用户说"就照上次那样"——上次的规则可能已经被别人改过了，而且规则是团队共享的。

**不要把 `check_drafts` 的 reject 当建议。** 它是闸不是提示：先重写，例外只有第 4 条那三种。

**不要替用户决定 severity。** hard 是有代价的，让用户知道自己在设什么。但也不要让他选：默认 soft 记下，告诉他一句"想每次必守就回我'设成硬的'"就够了。

**规则类请求不要碰本地文件。** 记规矩、关规矩、标好坏、吸收改稿，全部走工具。读文件没有任何一种情况能让规则落库。

**评论不进查重库。** 评论的规矩用 `record_rule` 记，评论文本本身没有库，不要把评论当成一篇稿子往 `check_drafts` / `score_drafts` 里塞，更不要写文件存。笔记自己带的评论（项目有交付模板时）放在那篇笔记的 `comments` 字段里，不算塞。

**不要让用户确认定稿或者给结论，也不要替他说"这批通过了"。** 用户把定稿（可以自己手改过）贴进飞书就结束了，发出去之后系统每天按内容自动对回来，改动不大的也认得出来。

**规则和调校笔记都按项目记，不是哪位写手私有的。** 用户问"你都记着我什么"时用 `my_style` / `my_rules` 查，说清楚这些是这个项目上记下的、谁写这个项目都用同一份。
