# 2026-11-14 审查修复：调校笔记的写回

这份说明讲的是 11-14 这一轮改动**合并之后**的样子。同一天早些时候另一份 AI（Codex）先推了一版，独立复查发现几处会出问题，
负责人决定由我们改掉；下面写的是改完之后的状态，末尾一节列出从那一版里拿掉了什么、为什么。

## 负责人要做的

在 Supabase 的 SQL Editor 里跑一次 `migrations/021_style_distillation_cas.sql`。

- **什么时候跑都行**，合并之前、之后都可以，和部署没有先后要求。可以重复跑。
- 它不改任何现有的调校笔记或精修，只加一个函数、换一个触发器。
- 跑完不用验收。想看就跑 `doctor`：「deskcore_save_style_cas（空笔记探测，不写行）」是 applied 就到位了。
- 没跑之前写作台照常能用：保存调校笔记走 021 之前的写法，服务日志里有一行「deskcore_save_style_cas 还没建」的警告
  （每个进程只响一次）。跑过之后自动改用新写法，不用重新部署。和这个分支之前相比有两处小差别，见下面第 3 条。

写手不用做什么。协议正文和 skill 版本没变（`6f23eba491fd`），不用重新导入 skill。

本次没有在生产库上执行任何 SQL。

## 改了什么

**1. 读旧笔记失败时，不再发一份「历史是空的」学习任务。**
以前读旧笔记出错会被当成「这个项目还没有笔记」，任务里的 `existing_notes` 是空的；模型照着它提炼，写回去的笔记会把旧笔记整份
盖掉。现在读失败和没有笔记分开：

- `record_edit`：精修照样存下来，回 `stored=true, distillation_status=pending`，告诉模型稍后调 `my_style` 接着做，
  不要重传同一条精修，也不要说已经吸收。
- `save_my_style`（不带 `edit_ids` 的手动改笔记要先读一次当前版本）：读不到就不保存，回一句模型看得懂的话，叫它稍后原样再调一次。
- `my_style`：如实说这次没读到，不显示成「没有笔记」。
- 写作简报（`open_project`）**不受影响**：这份笔记在简报里只是参考，读不到就记一条日志、不带它接着出简报，和以前一样。

**2. 写回按任务的版本比较。**
蒸馏任务多一个 `expected_revision`，和 `edit_ids` 一起原样传回 `save_my_style`。021 的函数在一个事务里比较版本、整份替换笔记、
只销这一批精修。两份任务前后脚写回时，先到的成功，后到的被拒（笔记和精修都不改），模型调 `my_style` 重取、基于新的
`existing_notes` 重新合并后再存。服务端不替模型合并文字。版本每次更新都往前走，同一个事务里连改两次、系统时间回拨也不会重复。

带了 `edit_ids` 却没带 `expected_revision` 的调用会被拒。拒绝的那句话写明下一步：调 `my_style`，用它回的任务里的
`existing_notes` 重新合并，再把那份任务的 `expected_revision` 和 `edit_ids` 原样带上重调。协议正文只提到 `edit_ids`，所以照旧
skill 做的客户端可能多走这一个来回；任务里的 `instruction` 和 `record_edit` / `my_style` 的 `next_step` 都写了要带版本。

**3. 021 没跑时退回原来的写法。**
只在「这个函数不存在」（PostgREST 的 PGRST202、Postgres 的 42883）时退回：整份覆盖笔记、按 id 销精修、不比较版本，写库的这一步
和这个分支之前一样。别的错误（权限、参数、库故障）照旧报错，不退回，也不会被说成「没跑迁移」。报错带错误码的只看错误码，
不看正文：正文里会印出项目、用户的 ID，里面碰巧有 42883 这几个数字不算数。

和这个分支之前比，没跑 021 时有两处不一样，都发生在写库之前，服务这时还不知道函数在不在：

- 带了 `edit_ids` 没带 `expected_revision` 的调用，跑没跑 021 都会被拒（见上面第 2 条）。没跑 021 时这次拒绝其实什么也没保护，
  代价是模型多走一个来回、重新合并一遍。
- 不带 `edit_ids` 的手动改笔记，会先读一次当前的笔记；这次读失败就不保存，回一句话叫模型稍后原样再调。这个分支之前是
  不读、直接写。

读旧笔记失败时，不管走的是哪条路（写作简报、蒸馏任务、手动保存），服务日志里都有一条带原因和栈的
「read user calibration failed」；模型只拿到那一句话，要查原因看日志。

## 从 Codex 那一版里拿掉的

**「硬约束拿不准」整项撤回**（`judge_client.py`、`deskcore/core.py` 的算分和话术、`deskcore/tools.py` 的两句说明、
`tests/test_judge_hard_ambiguity.py`、`tests/check_judge_contract.py`，以及为它改过的五个测试文件）。这些文件回到分支之前的样子：
Jev 拿不准、答案落在违规那一侧的硬约束，仍然是一条拿不准的硬伤，带着依据句和改法，模型照改；硬约束都答在合规那一侧的稿子，
分数和话术和以前一样。

撤回的原因：

- 它把负责人 11-04 定的规矩（W-42：合规上拿不准的也改，宁严勿松）反过来了。概率在 0.50–0.65、偏向违规的答案不再算硬伤，
  依据句和改法一起丢掉，还告诉模型不要改。
- 原来 100 分、有一道硬约束偏向合规但落在拿不准区间的稿子，会变成 92 分加一句「需人工复核」，而写手拿不到任何可做的事。
- 新话术里的「拿不准」和协议正文里的「拿不准的也改」撞在一起，同一篇稿子会同时收到「照改」和「不要改」。协议正文不能动。
- 它要求写作台和 Jev 按固定先后部署，顺序反了，拿不准的违规会被报成满分、全过。

这一项没有负责人的决定记录。要不要把「拿不准」单独交给人复核，留给负责人另行决定；在那之前维持 W-42。

那一版里「judge 回包形状不对算没打成分、不算干净」的加固没有单独保留：它新增的检查只针对新加的歧义字段，
和这项功能拆不开。分支之前已有的那部分（缺 `passed`、`hard_fails` 行形状不对都算 error）原样还在，测试也在。

**部署顺序的硬要求撤回。** 那一版要求先跑 021 再部署，函数不在时拒绝保存；合并先于 SQL 的话，每一次保存调校笔记都会失败，
报错还看不懂。现在顺序无所谓（上面第 3 条）。

**读笔记失败让 `open_project` 整个失败**的行为撤回（上面第 1 条最后一点）。

**CI 里删掉的断言补回来了。** 那一版把 ci.yml 里 171 行的「round-8 回归」换成 `tests/test_style_distillation_safety.py`，
但新文件少了几条：部分吸收后还剩几条要明说（`still_pending`）、手动改笔记不销账并提示（`note`）、`record_edit` 正常路径交出任务并
指名 `save_my_style`、任务材料里有标题和改稿备注、提炼口径由服务端给、空笔记拒收、`my_style` 的说明教模型看
`pending_distillation`、`save_my_style` 已注册、要身份、不吞异常、说明写清「完整笔记」。现在都在这个 pytest 文件里。
